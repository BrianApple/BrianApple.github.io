# 架构设计

IOTGate 网关与前置（master）服务、IOTGateConsole 管理平台组成典型的「终端 → 网关 → 前置」三级结构。

## 整体架构

- **感知终端**：通过 TCP 长连接接入网关，按各自规约（应用层协议）发送真实报文
- **IOTGate 网关**：负责终端连接的接入管理、多规约报文的拆包/黏包解析，并将真实报文按**自定义网关头**封装后转发给前置；同时作为被管理端接受 Console 的指令
- **前置（master）**：接收网关转发的数据，默认数据通道端口 **8888**；多个前置可组成集群，网关与前置通讯时默认采用**轮询方式负载均衡**
- **IOTGateConsole（可选）**：Web 管理平台，负责节点监控与规约远程管理，通过 **HTTP 指令通道（网关 10917 端口）**主动下发指令

入口类为 `Entrance.java`，通过命令行参数（`-n` / `-m` / `-k` / `-f`）决定网关的运行模式，详见[快速开始](./quickstart.md)。

```text
感知终端 ──(真实报文)──> IOTGate 网关 ──(网关头 + 真实报文)──> 前置(master) ──> 上层应用
                            │  ▲
                            │  │  HTTP 10917：Console 下发指令 / Console 探针取状态
                            ▼  │
                       IOTGateConsole（可选）
```

:::note 自 v2.0 起的架构演进
- **去除 Zookeeper 依赖**：集群模式改为 `-m` 直连前置（多个前置地址逗号分隔，数据通道零改动）
- **控制通道反转（v3.0.1）**：网关不再主动注册/上报状态，改由 Console **主动探针**（`GET /gate/status`）判活、**主动下发**（`POST /gate/command`）指令；原 RPC 端口 10916 与网关侧主动注册参数 `-c -r` **均已移除**
- **AI 智能体（v3.0.1）**：粘贴协议帧结构描述，大模型推导拆包/黏包解码参数并一键创建规约，见 [AI 智能体](./ai-agent.md)
:::

## Netty 高并发模型

IOTGate 基于 Netty 实现自定义协议的 TCP 长连接服务，具备以下高并发特性：

- **长连接保持**：终端与网关建立连接后保持在线，支撑大规模在线终端
- **自定义编解码**：Netty 的 handler 链完成报文的解码与编码，长度域驱动拆包/黏包处理
- **心跳机制**：单机版可在 `iotGate.conf` 中为每个规约个性化配置心跳周期；集群版默认心跳 **300 秒**

官方压测数据（Windows 笔记本、堆内存 2G、线程数 6K）：

- 单网关、单前置节点，每秒处理并发心跳 **8000+**
- **20 万**在线终端（长连接保持）时内存占用约 **1G**

## 多规约解析机制

网关通过配置文件 `iotGate.conf` 以「**一条规则 = 一个规约**」的方式管理多套解析参数，规则之间分号分隔。每条规则包含 9 个参数：

```properties
pId, isBigEndian, beginHexVal, lengthFieldOffset, lengthFieldLength, isDataLenthIncludeLenthFieldLenth, exceptDataLenth, port, heartbeat
```

网关启动时通过 `-f` 加载该文件（必选参数），每个规约绑定一个**独立的监听端口**，互不干扰。这些参数本质上是 **Netty 拆包/黏包解码（长度域解码）** 的配置项：通过**长度域偏移**与**长度域长度**定位长度字段，再结合**长度是否包含长度域本身**与**额外长度**计算出完整报文长度，从而正确切分数据帧。

各参数含义、取值与常见配错后果详见 **[iotGate.conf 参数详解](./reference/iotgate-conf.md)**。

:::warning
长度域相关参数一旦配置错误，网关将无法正确拆包，**终端与前置之间的数据链路会直接异常**。建议接入新规约前先仔细阅读协议文档中的帧结构定义，或使用 Console 的 AI 智能体辅助推导。
:::

## 终端接入（真实报文解析）

终端与网关通信时传输的报文称为「真实报文」，规约不同则报文结构差异明显。配置文件默认支持两种真实报文结构：

**规约编号为 1 的报文结构：**

| 报文属性 | 字节数 | 含义 |
|---|---|---|
| `68` | 1 byte | 报头 |
| `len` | 2 byte | 长度域：传输帧中除起始字符 68 和结束字符 16 之外的帧字节总数，包含长度域本身字节数 |
| `data` | n byte | 报文内容 |
| `16` | 1 byte | 报尾 |

**规约编号为 2 的报文结构：**

| 报文属性 | 字节数 | 含义 |
|---|---|---|
| `len` | 4 byte | 长度域：值为 data 的字节数，不包含自身字节数 |
| `data` | n byte | 报文内容 |

完整帧结构、帧长计算规则与内置规约示例详见 **[真实报文帧结构](./reference/real-message-frame.md)**。

## 前置通信（自定义网关头）

网关与前置通信时，会在真实报文前封装自定义的**网关头**，用于网关登录和携带网关自身与终端响应参数。网关头报文结构（**当前版本固定 30 字节**）：

| 报文属性 | 字节数 | 含义 |
|---|---|---|
| `AB` | 1 byte | 报文头（固定 `0xAB`） |
| `len` | 4 byte | 长度域：真实报文长度，包含"68"、"16" |
| `type` | 1 byte | 报头类型（`01` 真实报文 / `03` 登录） |
| `protocolType` | 1 byte | 协议类型（bit7 为 0 表示 IPv4、1 表示 IPv6；剩余 7 个 bit 表示规约类型编号） |
| `gateNum` | 1 byte | 网关编号 |
| `00*12` | 12 byte | 若 ip 格式为 IPV4，则为 12 字节 0；反之当前 12 字节 + 后续 4 字节存放 IPV6 的值，存放顺序从左至右 |
| `clientIP` | 4 byte | 终端的 IP 地址，ip 地址的每个段位占一个字节（不含符号和端口号） |
| `port` | 2 byte | 终端对应的端口号 |
| `count` | 4 byte | 终端与网关建立连接时对应的连接序号（1-10000 循环） |

网关启动时会向前置发送**登录报文**完成注册，规则如下：

1. 登录时长度域为 0；有真实报文时，长度域为整个真实报文长度值
2. 登录时 `type = 03`、`protocolType = 15`、`count = 1` 都为固定值；发送真实报文时 `type = 01`、`count = 终端与网关的连接序号`
3. 前置发现报头长度为 0 且 `type = 03`、`protocolType = 15` 时，不会执行解析数据的方法；否则继续解析真实报文

:::tip 完整规格见参考资料
字段偏移量、字节序（`len`/`port`/`count` 均为小端）、`type` 与 `protocolType` 取值表、IPv4/IPv6 布局对照、**十六进制组包示例**、前置侧解析步骤，以及**老版本 `0xA8` 报头差异**，统一收录在 **[网关头（A8 / AB 报文头）帧结构](./reference/gate-header.md)**。
:::

## GATE CLUSTER 三层结构

![集群版 IOTGate 架构](/img/iotgate/cluster-arch.jpeg)

GATE CLUSTER 由三层组成：

- **感知终端**：物联感知设备，与网关建立长连接，上报心跳与真实报文
- **GATE（IOTGate 网关）**：终端接入层，支持单机与集群部署，通过 `-m` 直连前置，集群版默认心跳周期 300 秒
- **GATE CLIENT（IOTGateConsole）**：Spring Boot 3.5 Web 工程（项目地址：https://gitee.com/willbeahero/IOTGateConsole ），用户登录之后可以查看当前 GATE CLUSTER 的运行状态监控，并可执行网关规约解析服务的启动、关闭、新增、删除等操作

各层职责：

| 层级 | 组件 | 职责 |
|---|---|---|
| 接入层 | 感知终端 | 建立长连接，按规约上报心跳与真实报文（modbus TCP / IEC 104 / DLT 645 等） |
| 网关层 | IOTGate | 终端接入与报文解析，网关头组包，登录前置，集群负载均衡（轮询），心跳保活 |
| 管理层 | IOTGateConsole | 节点监控、规约启停管理、AI 智能体、SSE 实时推送 |

:::note
图中 GATE CLIENT（项目名称"IOTGateConsole"）即管理平台。**网关侧无需配置 Console 地址**：由 Console 的「节点管理」页登记网关 IP 后，Console 每 10s 探针判活并主动下发指令（详见[部署指南](./deployment.md)）。
:::

## kernel 服务模式

IOTGate 最新支持与 master 节点通信的 **kernel 模式**。下图中，红色实线框部分为 **normal 部署模式**，黑色虚线框部分为最新支持的 **kernel 模式**，即 master 节点和所有的感知终端统一作为与 IOTGate 服务网络通信的客户端服务：

![kernel 服务模式](/img/iotgate/kernel-mode.png)

| 部署模式 | 说明 |
|---|---|
| **normal 模式** | master 节点作为服务端，IOTGate 与感知终端作为客户端接入（红色实线框部分） |
| **kernel 模式** | master 节点和所有感知终端统一作为与 IOTGate 服务网络通信的客户端（黑色虚线框部分），通过 `-k` 命令行参数开启，默认端口 10915 |

## 端口规划

| 端口 | 用途 |
|---|---|
| **8888** | 前置(master)数据通道（`-m` 参数直连，默认端口） |
| **10915** | kernel 模式默认端口（`-k` 参数开启） |
| **10917** | **指令服务**（Console → 网关）：`POST /gate/command` 下发指令、`GET /gate/status` 取运行快照。可用 `iotGate.conf` 的 `commandPort` 改端口，`commandToken` 开启 `X-Gate-Token` 鉴权（默认关闭） |
| **9811 / 9812 / 9813 …** | 各规约对应的**终端接入端口**（由 `iotGate.conf` 每行的 `port` 字段决定） |
| **8686** | IOTGateConsole 管理平台默认端口 |

:::warning 已废弃端口
**10916（原集群 RPC 端口）不再监听**。若有防火墙策略或巡检脚本按 10916 判活，需同步调整；同时原 `-c` / `-r`（网关主动注册到 Console）参数**已移除**，传入会打印「启动参数错误」并以非 0 退出。
:::

:::tip
集群模式下，网关与前置通讯默认采用**轮询方式负载均衡**；v2.0 起去除 zookeeper 依赖，通过 `-m` 逗号分隔直连多个前置，数据通道零改动。
:::
